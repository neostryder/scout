# Changelog

## [Unreleased]

### Added

- [Visible] [Software] **A research session can drive the competitor queue from the command line.** `node packages/cli/src/competitor-run.ts queue` lists queued runs, and `claim`, `complete`, `fail`, `list`, `gate`, and `watch` take JSON arguments and run the matching MCP tool, so a session without an MCP connection can still finish a run. `probe` reads one watch source with the hub's own rules and saves nothing.
- [Visible] [Software] **The research gate is editable from the Competitors page, the REST API, and MCP.** Update rules on the page, `POST /api/competitors/gate`, and `scout_competitor_gate` each write `competitors.json`. A rule can apply to every competitor or to just one, and clearing a field restores its default. An unknown field or a wrong type is refused, and the file keeps its old contents. Because the hub reloads the file right after a save, new rules take effect at the next check, sync, or update.
- [Visible] [Software] **A competitor with no public repository can be watched through a web page or a JSON feed.** A `watch` on the entry reads a version from JSON, reads a version from a page, or notices any change to a page's text, on the same 6-hour check as repositories. The first reading is the baseline, and a higher version later marks the competitor New and goes through the gate. A changed page with no version waits for Update. Only public https addresses are fetched, with each redirect checked, a 1.5 MB cap, and a 20 second timeout.
- [Visible] [UI] **The Competitors page edits the research rules and sets a watch source for a row without a repository.** Update rules, beside Check now, opens one field per rule for all competitors or for one, and an empty field shows its default. A row with no repository offers Watch a page, then says what it watches in place of the mirror sync line. Its Update button works without a mirror: it reads the page and queues research. A baseline taken from a page with no version shows as "page seen" and the date.
- [Visible] [MCP] **Two new tools change the competitor registry.** `scout_competitor_gate` with no arguments reads the research rules, and with `set` or `clear` it changes them for all competitors or for the one named by `id`. `scout_competitor_watch` sets the watch source for a competitor, and a `watch` of `null` removes it. Both write `competitors.json`, and an invalid value is refused with the file left as it was.
- [Visible] [UI] **The install detail pane shows upstream facts for a git clone or a Hugging Face model.** For a clone it names the default branch, the head commit date, the latest release, how many commits the clone is behind, and whether a newer release exists. For a model it shows the latest revision, whether a newer one exists, the quantizations the repository offers, related models, and possible successors. A repository Hugging Face does not list, or one that is gated, gets a single plain line.
- [Visible] [Software] **A competitor entry can follow an upstream that republishes its history.** Set `followUpstream` on the entry and the mirror sync moves to the new tip instead of refusing, after keeping the old tip on a `scout-before-rewrite/` branch. Entries without the field behave as before.
- [Visible] [Software] **The clone scan finds repositories under `~` roots on macOS and Linux.** The probe stripped the leading `~/` from a root with a pattern that Bash expands to the home folder first, so every `~/...` root resolved to a path that does not exist and those machines reported no clones. The probe now strips two characters instead.
- [Visible] [Software] **Mirror sync no longer fails when an upstream moves a tag.** Projects that republish a tag such as `latest` made `git fetch` refuse the update, so the mirror stayed behind and the row showed a wall of fetch output. The sync now updates moved tags, and a failure shows the lines that explain it.
- [Visible] [Software] **The Windows model scan finds Cogitator after it moves to another drive.** The probe checks `COGITATOR_HOME`, the install named by the Cogitator scheduled task, the per-user folder, and a `Cogitator` folder at the root of each fixed drive, and it scans the `data_dir` named in `cogitator.toml`. Before this, a moved install read as "Cogitator is not installed".
- [Visible] [Software] **A machine can add folders to its clone roots with `extraCloneRoots`.** The folders are added to the defaults, or to an explicit `cloneRoots` list, so a folder such as `~/_resources` can be opted in without listing every default again. A folder whose name starts with `_` or `.` is entered when it is named there.
- [Visible] [Software] **Scout syncs competitor mirrors on a schedule and queues research when the change is large enough.** Every 12 hours it fast-forwards one mirror at a time, with 2 seconds between mirrors and 120 seconds for each mirror. It syncs a mirror whose latest commit differs from the last synced commit, and once a week it syncs every mirror. A gate queues research after 5 commits or 3 changed source files, or on a new stable tag, once the last commit is 24 hours old. Docs-only and dependency-only changes are skipped, and at most 5 runs sit in the queue. The request already holds an analysis of commit types, file categories, a 0 to 100 change score, manifest changes, new hosts, new settings, and pricing lines. Update still pulls and queues immediately.
- [Visible] [UI] **The Competitors page shows mirror sync, a waiting line, and whether research was queued by hand.** Each row says when the mirror was synced, or the sync error in plain words. A change below the gate says how many commits are waiting. The research state says Auto-queued or Manual. The update confirmation says the pull ignores the usual wait.
- [Visible] [MCP] **The competitor queue reports the analysis the hub already computed.** `scout_competitors` includes mirror sync and any pending gate. `scout_competitor_queue` includes each run's trigger, and the request includes `analysis`. The queue fills itself when the gate says the change is worth research.
- [Visible] [Software] **Scout watches competitor repositories for a version newer than the last analysis.** The registry is gitignored `.scout-data/competitors.json`, written by `node packages/cli/src/competitors.ts seed`. The hub checks GitHub, GitLab, Codeberg, and Bitbucket remotes every 6 hours and sends one notice when a competitor is new, then again only for a later version. Update fetches the local mirror and queues a research request. Scout does not run that research, edit dossiers, or push. `--no-competitor-watch` turns the schedule off.
- [Visible] [UI] **The portal has a Competitors view.** It lists each competitor with the organization, the last analyzed version, the latest version, and the research state in ordinary words. The count beside the name is how many have a new version. Search matches the name and the organization, and New only starts on when any row is new. Update asks for confirmation, then pulls the local mirror and queues a research request. Nothing is installed, and the research waits until a person picks it up. A row with no local mirror shows Update disabled and the reason next to it. Check now starts a check of the remotes. On a phone the rows are cards, and the page is in the More sheet with the same count. When competitor watch is not set up, the page says to run the seed command.
- [Visible] [MCP] **An agent can read the competitor list and move a research run's state.** `scout_competitors` lists competitors, and `scout_competitor_queue` lists queued or claimed runs. `scout_competitor_claim`, `scout_competitor_complete`, and `scout_competitor_fail` record a claim, a finished analysis, or a failure. Those three change the run's state in the catalog and leave files, repositories, and machines alone.
- [Visible] [Software] **Scout catalogs local git clones.** Each machine lists clones under `~/Repositories`, `~/repos`, `~/src`, `~/code`, `~/git`, `~/Projects`, `~/projects`, and `~/dev`, plus each `projectRoots` folder, unless `machines.json` sets `cloneRoots`. A row records the path, remote, commit, branch, default branch, how far the clone is ahead of or behind the already-fetched upstream, and the newest tag the clone can see. A GitHub remote is also checked for its latest release and for how far that commit is behind the default branch. Scout does not fetch or update a clone. A folder whose name starts with `_` or `.` is skipped unless `cloneRoots` names that folder.
- [Visible] [Software] **Scout catalogs Cogitator model files and checks their Hugging Face sources.** The read-only source records quantization, size, modification time, engine roles, and provenance, with companion files grouped under their model. Research records newer revisions, related variants, and possible successors without downloading or updating weights.
- [Visible] [Software] **The hub scans the catalog on its own schedule, and remote machines can be paused.** With `--production` or `--schedule`, the hub scans each enabled host every 6 hours, starting 3 minutes after startup, and retries failed scans. `--scan-interval HOURS` changes the interval and `--no-scan-schedule` turns automatic scans off, while `GET /api/scans` shows scan status and `POST /api/scans/run` starts a scan by hand. Adding `"paused": true` to a remote machine in `machines.json` stops every connection to it and keeps its catalog history. Services shows a paused machine as Paused, and Resources hides its saved meter card.
- [Visible] [Services] **A new script, `tools/install-app.ps1`, installs Scout on Windows as a per-user app that starts at logon.** It copies the code to `%LOCALAPPDATA%\Scout`, installs production dependencies, brings `.scout-data` across on the first install, and registers hidden logon tasks for the hub and the watchdog that restart after a failure. The installed copy holds the live catalog, settings, and logs, so the repository can be moved or deleted. Running the script again after a pull updates the code and keeps the data.
- [Visible] [Services] **The hub raises an alert when the Galadriel backup is critical or its service stops.** Scout reads Galadriel's `health.json` every minute and shows "Backup unhealthy" on the Alerts tab for the hub machine while the level is critical or the file has gone 3 minutes without a rewrite. One notice goes out when the alert is raised and another when it clears, and a machine without Galadriel raises nothing.
- [Visible] [Services] **Linux machines show their listening TCP ports.** Scout reads them with `ss`, trying passwordless `sudo -n` first without ever prompting for a password, and each row shows the process name and PID. When the process belongs to another account or to a root service read without sudo, the row is named after the systemd service that owns the socket and the PID is blank. A socket shared by an nginx master and its workers shows the master, and published Docker container ports now appear on Linux as well.
- [Visible] [Software] **Arch Linux packages appear in the inventory.** A pacman adapter lists every installed package with its version, description, homepage, architecture, and whether it was installed explicitly or as a dependency. Packages that no sync database carries, usually ones built from the AUR or locally, are listed under the ecosystem "aur", and all others are listed under "pacman". Linux hosts are scanned by both dpkg and pacman, and whichever package manager is absent reports as skipped.
- [Visible] [Services] **Listeners owned by administrator, system, or other-account processes show a name.** On Windows, the probe reads the socket owner table and the service table, neither of which needs administrator rights, and names each row after its service or a known system owner. On macOS, a netstat section adds listeners from all accounts, including root, that lsof missed. The name is stored in a new searchable `owner` column and shows in the tray, the ports report, and the control confirmation. The Listeners table on the Services page gains a PID column. The first scan after upgrading can raise a one-time burst of "New listener" alerts for listeners that were hidden before.
- [Visible] [Services] **Linux machines now show their systemd service units in the Services view, alongside Windows services, scheduled tasks, and launchd jobs.** Scout gets loaded units from `systemctl show` and units that are installed but not loaded from `systemctl list-unit-files`. It skips static, alias, generated, and template units, and it runs from a non-root account. Core units such as `systemd-*`, dbus, polkit, and NetworkManager count as essential, so they are hidden by default. An outage alert fires only for an enabled unit of a long-running type. Scout cannot start, stop, restart, or disable systemd services yet.
- [Visible] [UI] **The tray panel opens on the tab for the computer it runs on.** The first time it opens, the panel picks the machine whose id or name matches this computer's short host name, and after that it keeps whichever tab you chose. If no machine matches, it opens on the tab that most needs a look, as before.
- [Visible] [UI] **On a phone, the Services view opens filtered to the hub machine.** On a screen narrower than 720 pixels, a link with no machine in it shows only the hub's services, and choosing All machines in the menu shows every machine again. A link that names a machine, or any wider screen, works as before.
- [Visible] [UI] **A new script, `packages/tray/tools/make-mac-signing-identity.sh`, creates a local code-signing identity for building the tray on a Mac.** The identity is named "Scout Local Signing" and lives in its own keychain with an empty password that never locks. Builds signed with it keep the same designated requirement, so the Keychain remembers Always Allow for the saved hub secret across rebuilds. Without it, each build is signed ad hoc and the Keychain asks once after every build.

### Changed

- [Visible] [Services] **Automatic-start updater services are no longer watched for outages.** A Windows service with "update" or "updater" in its name or display name, such as the Google Updater services, starts automatically, checks for a new version, and exits, so a stopped one is its normal state. Each of these used to open an outage when it finished. A watch switch set to true in `watch.json` still watches one.
- [Visible] [Services] **Dynamic-range listeners no longer raise alerts on any interface.** Listeners on ports 49152 and up no longer produce "new listener" or "listener exposure widened" alerts, whether they bind to loopback, the LAN, or all interfaces; before, only loopback listeners in that range were ignored. Apps such as Telegram and Thunderbird open temporary ports there, which filled the Alerts tab with noise. A listener in that range that a Cloudflare route or tunnel points at still alerts, and any open alert for an ignored listener resolves on the next check.

### Fixed

- [Visible] [Services] **A port that keeps listening under a different owner name no longer raises an outage.** Windows sometimes reports a listener's owner as process 0, which names the row "Idle" and changes its watch key. The row then ended and an outage opened although the port never stopped listening. A listener row now counts as down only when nothing is listening on its port.
- [Visible] [Services] **The hub no longer freezes for several seconds at a time on a large catalog.** The alert check runs on every live scan and health cycle, and it used to search the full service and listener lists one entry at a time for each of the tens of thousands of stored alerts, while every service and listener description repeated a linear search over install and project locations. On a catalog with about 17,000 old new-listener alerts, 16,000 listeners, and 20,000 services, the event loop stalled for up to 12 seconds, so the hub's own health probes timed out and raised false "domain origin down" alerts, outage alerts, and desktop notices. Lookups now go through indexes built once per check, which cuts the longest measured stall from about 12 seconds to about 1 second and leaves the hub idle about 92 percent of the time instead of about 43 percent. Alert checks requested within two seconds of each other, such as several machines finishing a scan together, now run once.
- [Visible] [UI] **On macOS, the Keychain no longer asks for the password every time the tray app starts.** The app is now signed ad hoc as a whole bundle, so its signature is valid and it carries the identifier `dev.neostryder.scout-tray`. Before this fix the bundle signature was broken, and choosing Always Allow did not stick. Each new build has its own signature, so the Keychain still asks once after an update.
- [Visible] [UI] **The tray panel no longer shows the connection screen at start when credentials are saved.** The panel could read its first status before the first hub check finished, open the connection screen, and leave it up. The connection screen now closes by itself once the hub answers.
- [Visible] [UI] **The tray panel opens the connection screen by itself when no credentials are saved or Cloudflare Access refuses the token.** It opens once for each problem and shows the refusal message at the top of the screen.
- [Visible] [UI] **The tray panel tries again every two minutes to read a saved secret it could not read at start.** A locked keychain is one cause. Each attempt and its result are written to `panel.log` in the config folder.
- [Visible] [UI] **The tray panel now opens on macOS.** It appears centered below the menu bar icon, whether from a left click or from Settings, Quit, or Open Scout in the right-click menu, and stays on the monitor where the icon sits. Before this fix the panel was placed above the top edge of the screen and never showed up. On Windows the panel still opens above the taskbar icon.
- [Visible] [Services] **A listener whose process name becomes known between scans no longer raises a "new listener" alert and a "listener gone" alert for the same port.** Scout used to record such a listener as a gone listener plus a brand-new listener, for example after a probe improvement or when sudo became available. Scout now renames the existing row in place, so learning a process name raises no alert.

## [0.2.0] - 2026-10-11

### Added

- [Visible] [UI] **The portal has a phone layout.** On a screen narrower than 720 pixels, the top navigation becomes a tab bar along the bottom with Services, Resources, Alerts, Outages, and More, and More opens a sheet with Updates, Catalog, Review queue, Jobs, and Settings. The Alerts tab shows how many alerts are open. The Catalog and Updates tables show each row as a card, and the detail panel fills the screen.
- [Visible] [UI] **A density button in the header switches between Auto, Comfortable, and Compact.** Comfortable gives rows more height and makes touch targets 44 pixels, Compact keeps the tight desktop look, and Auto uses Comfortable on a touch screen and Compact with a mouse. Each browser keeps its own choice.
- [Visible] [UI] **The portal still opens when the hub cannot be reached.** The service worker saves every page file and every successful API read that passes through it, and shows those saved copies when the hub does not answer. A gold strip then says "Offline, as of" with the time of the oldest saved answer on the screen, and every control that would change something is dimmed and turned off. When the hub answers again, the strip offers a reload. Only pages opened while the hub was reachable have a saved copy, and each browser keeps at most 200 saved answers.
- [Visible] [UI] **A command palette finds a port, machine, service, or page and jumps to it.** Ctrl+K, Cmd+K on a Mac, or the magnifier button in the header opens it, and a port can be typed as "port 4870", ":4870", or just the number. Every result is a link, and nothing in the palette can start, stop, or change anything.
- [Visible] [Services] **Each machine on the Services map shows how many of its ports other machines can reach.** A line on the machine's island gives the number of listening ports and how many of them listen on the LAN or on all interfaces, such as "12 ports listening, 5 exposed".

### Changed

- [Visible] [UI] **The portal downloads less when it opens and each time it refreshes.** The code for the Services, Resources, and Settings pages loads the first time each page opens, so the first screen is smaller. The reads the page polls (overview, listeners, routes, health, ports, stacks, alerts, outages, resources, summary, installs, and updates) now carry an ETag, and a request for an answer the browser already holds gets a 304 with no body. Every other API read is still sent with `Cache-Control: no-store`.

### Fixed

- [Visible] [Services] **A service now claims the listeners that its child processes open.** Scout matched a listener to a service only when the service's own process held the port, so a service that starts helper programs, such as Cogitator and the two engines it runs on Bilbo, left those ports looking unowned and unwatched. The listener scan now records each listener's parent process on Windows and macOS, and a listener whose parent is a service that stays up is treated as that service's and watched for outages.

## [0.1.1] - 2026-10-11

### Fixed

- [Visible] [Services] **A port no longer shows up twice when Windows reports its owner as process 0.** Some Windows builds read the owner of a loopback listener as "Idle" on one scan and as the real program on the next, so the Services page listed the port under both names. Scout now keeps the last real owner it saw on that port.
- [Visible] [Services] **Short-lived high ports no longer raise outage alerts.** Cloudflare WARP opens a new port in the dynamic range on the LAN address every hour or so and closes it a minute later, and Scout reported each one as a service going down. Scout now skips any listener in the dynamic port range unless a container serves it.
- [Visible] [Services] **Services on the hub machine no longer flap between down and back up when Windows drops them from its listener list.** Some Windows builds leave loopback listeners out of that list or show them under an unknown owner, so running services looked stopped for a minute or two. Scout now connects to the port before it counts a listener on the hub machine as down, and a port that still accepts connections stays up.
- [Visible] [UI] **Saving the portal as an app on a phone keeps its icon.** The icons and the manifest were behind the Cloudflare Access sign-in, and a phone fetches the home-screen icon in a separate process that has none, so it got a login page. The page now carries its Apple touch icon and favicon inline, and the other icons and the manifest load without a sign-in from a bypass rule that names those paths. The hub serves only those paths without a token.

## [0.1.0] - 2026-10-11

### Added

- [Visible] [UI] **Scout has a new app icon, a stone watchtower with a glowing lantern on a gold hexagonal badge.** The badge sits on a dark teal rounded square, with two green banners and an emerald over the tower door. Every other size, from the favicon to the tray app's Windows and macOS icons, is generated from `packages/web/public/icon.svg` by `node tools/make-icons.mjs`. The web page now links a web app manifest, so a browser can offer to install Scout as an app. The tray app's executable, installer, and shortcuts use it too, and the status icon in the notification area is now a small gold-and-amber watchtower beside the same green, amber, red, or grey status marker.
- [Visible] [UI] **A Resources page shows how busy each machine is.** It sits beside Services in the top navigation, with one card per machine that gives its operating system, the age of the reading, and a one-line summary. Each card has rows for Processor, Memory, each disk, Video memory and Graphics for each NVIDIA card, and Network, and each row shows a bar, a number, and, except for disks and video memory, a half-hour chart. A row turns amber and says High at 70 percent, and turns red with a striped bar and says Very high at 85 percent. Selecting Processor or Memory lists the five processes using the most of it on that machine, and a process that belongs to a running service or an open listener in the catalog shows that name instead of its process name.
- [Visible] [Services] **The hub reads processor, memory, disk, graphics, and network use from every machine.** It uses the connection Scout already has for each machine, locally on the hub machine and over ssh for the others, and runs one fixed read-only script per operating system. Readings arrive every 60 seconds, or every 10 seconds while the Resources page is open. A machine that cannot be read keeps its last reading, which is marked Stale after 150 seconds, and the other machines carry on. `--no-meters` turns metering off.
- [Visible] [UI] **Scout sends you a notice when a disk is nearly full, memory is under pressure, or video memory is nearly used up.** A notice goes out once a meter has stayed at or over its threshold for a set number of minutes: 90 percent for 5 minutes for each disk, 92 percent for 10 minutes for each machine's memory, and 95 percent for 10 minutes for each graphics card's video memory. Each episode sends one notice through the same desktop notification and Discord webhook as outage notices, and one "back to normal" notice follows once the meter falls 5 points under the threshold. The Alerts section on the Resources page turns each rule on or off and changes its percentage and minutes, and the same settings are kept in `.scout-data/meter-alerts.json` on the hub machine.
- [Visible] [UI] **The tray panel shows how busy the selected machine is.** A strip under the machine tabs has rows for Processor, Memory, the busiest disk, and Video memory, each with a bar and a percentage. A row turns amber and says High at 70 percent, and turns red and says Very high at 85 percent, the same as on the Resources page, and a reading older than 150 seconds is dimmed. The tray icon's tooltip also lists each machine that has a reading, for example "Eru 12% CPU 38% RAM 20% VRAM", with the VRAM figure only on machines that have a graphics card.
- [Visible] [UI] **The tray panel starts when you sign in and starts again after a crash.** The installed app registers itself each time it starts: a per-user scheduled task named "Scout Tray" on Windows, and a LaunchAgent on macOS. A development build registers nothing. "Start at login" on the tray icon's right-click menu is on by default and turns this off or back on. Quit asks for confirmation first, and after Quit Scout the tray stays closed until the next time you sign in.
- [Visible] [Services] **You can disable and enable launchd jobs and scheduled tasks from Scout.** Disable stops the job and keeps it from running again until you enable it, and both actions go through the same plan, confirmation, and audit log as start, stop, and restart.
- [Visible] [Inventory] **Scout scans your machines and lists the software on each one.** It reads Windows (registry, winget, Store apps, WSL, Docker Sandboxes), macOS (apps, Homebrew, casks, pkgutil, launchd), npm, pipx, and uv tools, Go and local binaries, language runtimes, container images, and dpkg packages on Linux. Remote machines are read over ssh, and a scan never starts a program or a guest.
- [Visible] [UI] **A page on the hub machine shows the whole catalog.** It has Catalog, Updates, Review, Jobs, and Services views with live search, filters you can save, and a detail panel for each install. The Review view lets you confirm or reject installs that Scout thinks are the same program.
- [Visible] [Research] **Scout finds the newest version of each install.** It asks Homebrew, npm, PyPI, GitHub releases, the Go module proxy, crates.io, Sparkle appcasts, winget, and the Store, and shows end-of-life dates from endoflife.date as notes.
- [Visible] [Updates] **You can update installs from the page.** Scout shows the exact winget, Store, brew, cask, npm, pipx, or uv command, waits for you to confirm, and then runs a check, the update, and a verify step for one job at a time on each machine. The Updates list is sorted by a priority score by default.
- [Visible] [Updates] **Updates that would break other software are refused.** If an update would break a runtime another program needs, Scout refuses it, and smaller risks ask for a second confirmation. Version pins in your project files show up as notes.
- [Visible] [Updates] **Apps with no package manager can get their installer downloaded.** Scout saves it to that machine's Downloads folder after checking its size and checksum, and leaves running it to you.
- [Visible] [Services] **The Services view shows what is running and listening on each machine.** It lists open ports, Windows services, scheduled tasks, and launchd jobs, marks each as essential, optional, or third-party, and gives each a short description you can edit.
- [Visible] [Services] **You can start, stop, and restart services from Scout.** Each action shows a plan first, needs a one-time confirmation, and is logged. Scout will not stop anything on its protected list, such as ssh, remote access, the tunnel, or Scout itself, and it gives uninstall steps as text only.
- [Visible] [Services] **A Windows hub machine can start your own projects.** Scout finds package scripts, launch configurations, and compose files in your project folders and runs each one only after you approve its exact command. Stacks start several of them in order and wait for each port to open.
- [Visible] [Services] **Alerts tell you when something changes.** They cover new listeners and background jobs, stopped services, sites that are down, ports that became reachable from more places, failing health checks, certificates that expire within 14 days, crash loops, and port clashes with your ports registry. You can acknowledge or mute each one.
- [Visible] [Services] **Installs, services, and listeners carry provenance flags.** Odd location marks something installed in or running from a temp folder, a Downloads or Desktop folder, the shared Public folder, or the Recycle Bin. No publisher marks a Windows uninstall entry that names none, Not signed marks a Store app package with no signature, and Mine marks what belongs to your own projects. Each flag shows its evidence as hover text and in the detail panel's Provenance list, and no flag changes anything on a machine.
- [Visible] [Services] **The `provenance` CLI command shows which projects are yours.** It lists each project's git remote, last author, and whether it counts as yours, `provenance scan` reads the git facts again, and `provenance flags` lists flagged installs with their evidence. Your projects are named by an optional `.scout-data/mine.json` holding your GitHub owners and git author emails.
- [Visible] [Services] **Scout watches for outages and records each one.** Every 2 minutes the hub checks each machine's ssh port for an SSH greeting, the public hostnames it health-checks, and the services and ports it has seen running. A machine that accepts a connection but sends no greeting counts as hung, and an outage is confirmed after 2 failed checks in a row, so a quick restart raises nothing.
- [Visible] [Services] **The Services page has an Outages tab.** It lists open and past outages, shows the status of each notice channel, sends a test notice, pauses the watch for 1 or 8 hours, and turns checks on or off by kind, machine, or item. The `outages` CLI command lists outages, pauses and resumes the watch, and changes the same switches.
- [Visible] [Services] **Outage notices reach your desktop and Discord.** Each outage and its recovery show a desktop notification on the hub machine, and a Discord post when `SCOUT_DISCORD_WEBHOOK` holds a Discord webhook address. Outages also appear on the Alerts tab as high-severity alerts.
- [Visible] [Services] **A watchdog reports when the hub itself stops.** `pnpm --filter @scout/hub watchdog` (on Windows, `tools/run-watchdog.ps1` keeps it running) runs as a second login service on Windows, macOS, or Linux and sends a notice when the hub's heartbeat goes stale, and a restarted hub records the time it was not running as a monitor gap.
- [Visible] [Services] **Outage notices and alerts show the time in the hub machine's time zone.** Outage notices, outage alerts, and unhealthy-endpoint alerts give local time to the second, such as 2026-10-10 15:26:03 MST, and end with the minutes since the last successful check, such as (4 minutes since the last successful check), or say that no successful check is on record. The watchdog notice uses the same time format.
- [Visible] [Services] **A pause in the hub no longer shows up as a site going down.** If a health probe times out or cannot connect while the hub itself was stuck for 0.75 seconds or more, Scout tries the probe once more before counting it as a failure.
- [Visible] [Services] **The hub no longer freezes for seconds after each live read of a machine.** Matching listeners to services, checking a machine for stored rows, evaluating alerts, and resolving stacks now work from one shared listing per pass. In normal operation on a catalog of about 6,500 services, the longest pause in the hub is now about 11 milliseconds, down from about 2.5 seconds.
- [Internal] [Services] **Outage notices read the last passing check from a new `last_ok_at` column.** The column sits in the `watch_state` table and holds the time each watched item last passed. - [Visible] [Services] **The outage watch covers only services and ports meant to stay up.** Scout watches Windows services that start automatically, launchd jobs with KeepAlive set, their listening ports, and ports served by a container or reached by a published route, so closing an app on purpose no longer raises an alert. ### Fixed

- [Visible] [UI] **Saving the portal as an app now picks up the Scout icon.** The page lists its 192 and 512 pixel icons as page icons, gives the manifest an `id`, and registers a small service worker that caches nothing, so a browser treats it as installable. The hub also lets a browser keep the icons and the manifest for an hour instead of marking them uncacheable.
- [Visible] [Services] **Reads and actions over ssh stop failing at random on a Windows hub machine.** The ssh program that comes with Windows exits with a crash code on about half of its runs, even after it has printed everything, so a finished read looked like a failure. Scout now runs the ssh that ships with Git for Windows when it is installed, which ran clean in every test, and the `SCOUT_SSH` environment variable names a different ssh program.
- [Visible] [Services] **Stop and Restart no longer give up when one read of a machine is slow.** If a probe is slow or dropped while a stop or restart plan reads the machine, Scout now reads it once more before refusing with "The machine state could not be read." A machine that cannot be reached at all still gets that refusal. The error had blocked Stop and Restart on a Mac reached over ssh.
- [Visible] [Services] **Listeners behind a Windows service wrapper show their real command.** When a wrapper such as shawl runs a program as a Windows service with administrator rights, Scout cannot read that process's command line, so its listener used to show as plain `node`. ARK Overseer on port 3310 was one of these. Scout now takes the real command from the wrapper's service entry, and the row shows the program path and the script it runs.
- [Visible] [Services] **Launch recipes start the real program instead of opening a script in an editor.** When `pnpm` or a similar command resolved to a `.ps1` script, starting a recipe opened that script in the editor set for `.ps1` files, and Scout reported the recipe as running even though nothing had started. The launcher now starts the matching `.exe`, `.cmd`, `.bat`, or `.com` file on PATH, and if no such file exists the action fails without launching anything.
- [Visible] [Services] **A recipe without a port is checked twice after launch.** The checks run about 3 and 8 seconds after it starts, and the result says whether the process was still running at 8 seconds or exited sooner. A stack that includes such a recipe now waits 8 seconds for it instead of 3.
